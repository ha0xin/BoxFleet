# 实时连接审计与断线恢复

日期：2026-10-07。状态：现状核查及设计建议；WebSocket 和磁盘队列尚未实现。

已完成的现成实现核查与复用选择见 [prior art 文档](telemetry-prior-art.md)：优先复用成熟 Go 传输/存储库及现有重试、认证和去重，不自行设计 WAL 文件格式。

## 当前通信与界面状态

agent → bfs 使用定时 HTTP 请求，默认每分钟拉配置、上报心跳、计费流量、连接和日志。HTTP 可以复用底层连接，但没有持续推送连接事件。sing-box → 本机 agent 使用 daemon gRPC 连接流，两段通信不同。

Network Events 新增 Status 列：

| 值 | 含义 |
| --- | --- |
| 活动中 | 会话尚未观察到关闭事件，是最后上报状态，不保证现在仍在线 |
| 已关闭 | 已观察到关闭事件 |
| Aggregated | 旧版多连接聚合桶，不能给整个桶一个会话状态 |
| Unknown | journal 或缺少状态的记录 |

正常情况下 “活动中”对应活动连接，但采集延迟、掉线或漏掉 CLOSED 都可能留下“活动中”。不能按等待时间自动伪造“已关闭”。未来增加独立的“最后观测时间 / 数据是否过期 / 节点在线状态”，保留未知状态，不把节点断线等价成连接关闭。

## 当前完整性边界

依据 `internal/agent/agent.go`、`connections.go` 和服务端 ingest：

| 故障 | 当前行为与缺口 |
| --- | --- |
| 服务端已收报告，HTTP 响应丢失 | 保留 PendingConnections 重发；服务端报告唯一键防止重复处理 |
| 短暂网络故障或 bfs 停机 | 已暂存的一批连接报告保留在状态文件，后续报告周期重试 |
| 长时间断线 | 已暂存报告阻塞新 Drain；采集器继续在有上限内存中累积，达到上限会丢弃，不能保证完整 |
| agent 正常退出 | 尝试保存最后窗口；若已有未发送报告，保留旧报告并丢弃最后窗口，不覆盖旧报告 |
| agent 崩溃/节点断电 | 已落盘报告可重试；尚在内存的事件可能丢失。仍运行的 sing-box 可提供部分状态重放，但回放范围有限 |
| sing-box 重启 | 在途连接状态和计数可能消失；不能保证补回终止时尾部数据，记录 reset/缺口 |
| journal 采集停顿 | 游标支持续读，但依赖源日志仍保留；轮转、清理或非持久 journal 会造成缺口 |
| 主机磁盘损坏 | 单机状态文件与数据库不能抵抗介质丢失，需要备份或复制 |

SaveState 使用 renameio.WriteFile。该库同步临时文件内容再原子替换；不要将其误说成纯内存保存或完全没有 fsync。原子替换也不能证明所有文件系统下断电后目录项一定持久，需验证目录同步和实际部署文件系统。状态文件保护的是已暂存报告，不保护还在采集器内存的所有事件。

当前计费仍用 v2ray 计数与 CounterEpoch。重启检测避免把计数回退当负增量，但不能恢复 sing-box 进程退出前尚未读取的全部计数；不可宣传为断电零损失。

## WebSocket 是否合适

可以增加 agent 主动发起的 WSS 连接，降低日志/连接更新延迟。认证沿用节点 bearer token，节点身份由服务端决定；已暂停、撤销 token 与删除语义必须继续遵守现有规则。

[WebSocket RFC](https://www.rfc-editor.org/rfc/rfc6455.html)定义双向消息传输，不提供跨重连的业务持久化确认。[Cloudflare 文档](https://developers.cloudflare.com/network/websockets/)说明其网络重启可能终止连接。因此重连、心跳和重放是必需设计，不能把长期连接当作永不掉线。

建议保留 HTTP 配置、更新与批量补传作为兼容路径；WSS 只作为新的低延迟发送通道。浏览器实时展示可以另用 SSE，界面刷新与节点数据采集不必使用同一个协议。降低 HTTP 上报周期并独立调度也是可评估的低复杂度过渡方案，实时并不强制要求 WSS。

## 先做可靠队列，再接实时通道

目标链路：采集 → 节点追加文件队列 → HTTP/WSS 发送 → 服务端事务提交或持久队列提交 → ACK → 节点回收已确认片段。

节点不部署数据库或 Docker。使用有上限的顺序追加分段文件，记录校验和、批次 ID、序号和确认水位。采集 Recv 路径不能同步等待磁盘，否则会阻塞 sing-box 流并导致上游漏采；需要有上限的交接缓冲与单独写盘工作线程，缓冲满时明确计数缺口。同步周期定义可承诺的崩溃损失窗口，不声称绝对零损失。

队列身份独立于进程重启；已经生成的报告 `(node_id, agent_boot_id, sequence)` 保持不变，序号及批次一起持久化。服务端事务提交前不 ACK；ACK 丢失时重发同一批次，重复返回成功。若 ACK 表示进入中央持久队列，应明确与“已经可查询”的区别，并监控延迟。

WebSocket TCP ACK 仅表示传输层接收，不等价于数据库落盘。禁止在发送成功时删除本地报告；只能在业务 ACK 后推进回收水位。HTTP 与 WSS 使用相同幂等键，避免回退通道导致双计数。新旧 agent 使用版本协商逐步升级。

限制批次大小、在途窗口、重连指数退避及随机抖动；避免实时消息逐条写数据库。积压补传与当前事件需要公平调度，计费和心跳不能被日志占满发送资源。

磁盘队列容量依据“峰值审计写入字节/秒 × 可承受断线时间”测量确定。达到上限时不能无限增长或阻塞代理业务；记录明确的丢失起止时间、数量和原因，保留 gap 标记以便恢复后上报。不同数据优先级明确配置，不能悄悄丢弃后仍报告完整。

服务端 SQLite WAL/同步配置、中央队列 fsync、ClickHouse 写入确认及备份应单独验证；节点保留未确认数据，不能补救服务端确认后又丢失磁盘的数据。

## 验收与实施顺序

1. 先上线 Status 展示，明确观测语义。
2. 实现有容量上限的节点文件队列与统一 ACK/重放协议，保留 HTTP。
3. 故障测试：提交后丢响应、agent kill/restart、服务器 restart、队列写入时断电模拟、部分尾记录、磁盘满、超时重试、长期断线、sing-box 重启和日志轮转。
4. 增加低延迟 WSS 通道；测试 Cloudflare/Tunnel 重连、重复补传、撤销 token 和旧版本回退。
5. 增加节点采集状态、最后报告时间、队列字节/年龄、确认水位、丢失区间和来源覆盖指标。

正确性目标是可观测的至少一次发送、服务端幂等应用及有界损失窗口。上游 sing-box 的静默漏采仍需明确披露；队列只能保护已经收集的数据，不能重新创造未采到的事件。
