# 节点地址发现与出口策略实施计划

日期：2026-10-18。状态：第一阶段代码已实现并通过本地功能验收，尚未部署；第二阶段仍为设计。当前行为和操作见 [节点地址发现](node-addresses.md)。本文保留设计依据及后续任务，不代表所有后续能力已承诺上线。

依赖选择、可参考的上游实现和只读 PoC 见 [开源复用调研](node-network-prior-art.md)。第一阶段已引入 Linux netlink 依赖，并升级现有 chi 至 v5.5.0，复用其可信代理来源解析；探测、重试、状态保存和前端沿用标准库及现有依赖。

补充需求：[Path 分组与组授权](path-groups.md)的基础能力已实现，与本计划的出口策略独立；本计划内的地址发现已完成代码实现，出口策略仍未实现。

## 1. 建议方案

按用户确认的顺序分为两个阶段：**第一阶段完成节点地址发现**，同时包含 agent 本机地址清单与 Server 公网来源观测；**第二阶段再实施出口策略**。第一阶段只保存当前状态，不保存 IP 变化历史，不修改入口地址或生成新的 sing-box 配置。

第一阶段交付：Linux 地址枚举和事件监听、变化后上报完整快照、周期校准、可信 Tunnel 来源解析、当前状态 API 和节点地址界面。节点侧需要升级 agent，不能仅靠 Server 观测代替本机采集。Server 收到新状态后更新管理页；“变动时通知 Server”不要求维护历史记录或另建通知中心。

第二阶段出口管理界面让操作者回答三个问题：

1. 从哪里出去：系统默认，或者某个具名出口。
2. 使用什么地址族：双栈、优先 IPv4、优先 IPv6、仅 IPv4、仅 IPv6。
3. 固定哪些源地址：IPv4 自动或指定一个地址；IPv6 自动或指定一个地址。

默认作用于某个用户在某个节点上的全部代理连接；需要时再加“只有这些域名、网段或端口使用此出口”的规则。入口地址继续由 NodeHost / Endpoint 管理。

第一版不建设通用 sing-box JSON 编辑器，也不默认打开 Clash API、自动探测所有目标或在节点安装数据库。

## 2. 当前实现与可复用部分

以本仓库当前源码为依据：

| 现有对象 | 当前职责 | 本方案处理 |
| --- | --- | --- |
| NodeHost | 管理员维护的客户端连接地址，可为域名、IPv4、IPv6 | 保留为入口发布配置；发现的地址单独保存 |
| Proxy | 节点上的监听、协议与凭据入口 | 保留；第二阶段不在这里增加另一层出口覆盖 |
| Endpoint / Path | 连接地址和客户端链路 | 保留；不把出口源 IP 塞进 Host |
| ProxyCredential | 渲染认证身份与计费计数器名称 | 用于把用户策略展开为 `auth_user` 条件 |
| PathAccess | 用户对产品线路的授权 | 不改变其语义，不当作服务端可识别的连接身份 |
| `node_outbounds` | 已有节点级出口表 | 补齐 facade、API、验证和渲染，优先复用 |
| `route_profiles` | 已有节点或全局规则模板表 | 用于保存结构化用户策略，增加显式格式版本 |
| `user_node_bindings.route_profile_id` | 已有策略关联列 | 补齐当前 facade 未暴露的读写能力 |

`RenderNodeConfig` 当前实际输出统一的 `direct` / `block` 和 `route.final = direct`；不能把已有表、JSON 字段或文档描述当作这些配置已生效的证据。现有 Proxy 的 `*_rules_json` 字段也没有形成完整的渲染管线，实现前须盘点存量数据，不能悄悄启用历史保存的任意 JSON。

第二阶段按“用户 × 节点”设置策略。不同用户可以共用同一 Proxy，但同一个用户若通过多个共享凭据的 Path 接入同一 Proxy，服务端不能区分他选了哪条 Path。要做按 Path 不同出口，必须另行设计独立凭据或独立入口，不隐式改变凭据和授权关系。

## 3. 地址发现：区分事实、探测结果和配置意图

### 3.1 地址范围

agent 发现的是本机已配置的地址，不是供应商分配的整个 IPv6 前缀，也不是所有潜在公网 IP。

- 本机地址：地址、地址族、接口、前缀长度、作用域，以及平台可提供的 tentative / deprecated / temporary 等状态。
- 公网出口观测：指定源地址访问探测服务时，对方看到的地址。它可能受 NAT 影响，与本机地址不同。
- 入口地址：管理员希望客户端连接的地址，仍为 NodeHost。出站探测成功不证明它允许公网入站。
- 未分配到网卡的路由 IPv6、NAT 映射地址可以作为说明或入口手动录入；第二阶段不允许据此绕过源地址绑定校验。

采集时保留接口及可用性字段，UI 默认突出可用单播地址，回环/链路本地等可在详情中查看。私网地址仍展示；不能因为不可公网路由就判为采集失败。第二阶段默认可选源地址排除回环、链路本地、未指定、多播和不可用地址，临时 IPv6 默认不推荐用于固定出口。

### 3.2 采集与上报

采用“完整快照 + 内容变化去重”，不维护复杂的地址增量日志：

- 启动时采集；Linux 优先通过成熟库监听网络地址事件，并每 30 秒校准一次。
- 无事件监听能力的平台退化为每 30 秒扫描；变化去抖建议 2 秒。以上为初始参数，部署测量后调整。
- 变化后独立上报，不等待配置轮询、日志上传或计费批次；全量快照每 5 分钟重新确认一次。
- 枚举不完整或失败时报告采集错误，保留上一次完整快照；只有明确成功的完整枚举才能确认地址移除。
- 断线期间合并为最新快照；本功能不保存或重放中间每次地址抖动，不建设地址事件账本。
- 上报失败退避重试；同一快照 ACK 丢失可重复发送，不能错误覆盖更新的当前状态。

拟增加 `POST /api/node/network-snapshot`，共享结构放入 `internal/model`。请求包含持久单调递增的 `revision`、采集时间、完整性、错误和地址列表；规范化内容 hash 由 Server 计算；Server 从 token 获取 node_id。

agent 单一发送者串行发送；revision 在发送前随轻量状态原子保存。Server 事务内接受新 revision、幂等确认同 revision 同 hash、拒绝同 revision 不同 hash，并忽略旧 revision 对当前状态的覆盖。agent 本地状态丢失时通过显式同步流程从 Server 获取新 revision 起点，不能仅靠时间戳或重启后归零。不同 agent 进程不得同时维护一个节点的快照。

初始边界建议：请求上限 256 KiB、最多 1024 个地址、接口名及其他字符串设长度上限；超过上限标记不完整，不把截断列表当作全量。节点只保存最近快照身份和少量重试状态，不引入数据库或专用 WAL。

### 3.3 外部出口探测

默认优先由 bfs 从已认证的 agent HTTP 请求中记录来源 IP 和 Server 观测时间，不额外请求公共服务。直连时读取 RemoteAddr；反向代理场景仅在显式可信入口配置下读取来源头。当前 Cloudflare Tunnel 部署应读取 CF-Connecting-IP，处理 Pseudo IPv4 覆盖模式中的 CF-Connecting-IPv6；不能无条件信任客户端传入的转发头。

2026-10-18 对当前生产链路做了只读检查：cloudflared 转发到宿主机回环端口 18081，bfs 仅将端口发布在回环地址；约 52 秒被动观察中，HK-G1、SG-G1、HK-AWSNAT、PH 的真实节点请求均包含 CF-Connecting-IP，并与 X-Forwarded-For 一致，也观察到其他节点使用真实 IPv6。节点归属通过请求 token 的摘要与现有未撤销 token 记录关联，未保存原始抓包或 token。bfs 容器的 TCP 对端是 Docker 网桥地址，不能直接作为节点出口。现有心跳处理尚未保存来源 IP；生产服务和配置未改动。实时 IP 不写入版本库。

此链路下的观测表示“节点访问 Cloudflare 边缘时的出口”，不是节点到 bfs 宿主机的直连出口。信任策略须覆盖本机 cloudflared 到容器的完整路径，不可简单放行所有私网网段。缺少或无效的可信来源头标记未知，不把网桥 IP 当公网 IP。现有 HTTP 复用连接只反映该连接的来源；检查新的出口选择需要新建连接。普通心跳也只观测实际使用的地址族。

需要另一地址族或指定源地址时，首先向自家可通过该地址族访问的观测端点发起绑定源地址的新请求。公共回显探测作为按需启用的补充，不是地址枚举的前提；不对每个 IPv6 高频发送请求。HK-G1、SG-G1、HK-AWSNAT、PH 为用户明确指定的 NAT 节点，本机私网地址、观测公网出口和手动维护的入口保持分离，IP 探测不需要端口映射规则。

- 显式绑定本地源地址，IPv4 / IPv6 分开测试。
- 使用受配置约束的 HTTPS 探测服务，限制响应长度、超时和并发，不接受节点上报任意 URL 要求 Server 代为访问。
- 建议每个启用探测的出口每 5 分钟一次，地址变化后补测，最多 2 个并发；失败显示失败原因及上次成功时间。
- 出口观测是目的地相关的样本；不能用某个探测服务的结果保证所有网站看到相同公网 IP。

### 3.4 Server 保存与显示

只保存当前状态：已新增 `node_network_snapshots`（最近 revision、hash、成功地址 JSON 集合和最近采集状态）和 `node_observed_ips`（按节点、来源、IP 保存的最近公网观测）。地址集合有 1024 条/256 KiB 上限，直接与版本元数据原子更新，不另建 node_addresses 表。不新增 address_changes/history 表、历史分页接口、历史清理任务或历史页面。

本机地址以 node_id、接口、规范化地址为身份；成功接收新的完整快照后，在事务内替换旧地址集合，移除已消失的地址。采集失败只更新错误及新鲜度，不覆盖最近成功快照。仅记录最近成功观测/接收时间，无需保存旧 IP 或旧快照。

agent 上报每个接口上的全部 IPv4/IPv6；公网观测也支持同一地址族的多个 IP，不按地址族覆盖旧值。公网记录 3 分钟未见标记 stale，下一次有效观测时移除超过 10 分钟未见的样本，每节点最多保留 128 个；离线时保留最后状态并标记过期。一次 IPv6 心跳不证明 IPv4 已消失。默认观测不代表枚举出所有 NAT 出口。第二阶段固定绑定保存明确的地址值，不通过保留失效 inventory 行来维持配置引用。新注册的同名节点使用新 node_id，不继承旧节点地址或策略。

在线状态与地址状态分开：节点断线后显示“数据过期”，不显示“所有地址已消失”。接收时间由 Server 记录，agent 时间仅作观测信息。

## 4. 第二阶段：出口配置

### 4.1 第二阶段基础出口字段

复用 `node_outbounds`，为 `direct` 提供以下受验证的配置；显示名和状态等必要字段通过追加迁移补齐。

| 字段 | 选择 | 约束 |
| --- | --- | --- |
| 地址族策略 | `auto` / `prefer_ipv4` / `prefer_ipv6` / `ipv4_only` / `ipv6_only` | 默认双栈，不改变已有行为 |
| IPv4 源地址 | 自动或一个本机 IPv4 | 与节点地址关联，同时保存明确的地址值 |
| IPv6 源地址 | 自动或一个本机 IPv6 | 与节点地址关联，同时保存明确的地址值 |
| DNS 配置 | 节点管理的解析器引用 | 第二阶段不让每个出口自由输入 DNS JSON |

地址族策略与源地址绑定是两个独立维度。只填写 IPv6 源地址时，双栈模式下 IPv4 仍按系统默认出站；选择“仅 IPv6”才禁止 IPv4。仅 IPv6 下填写 IPv4 绑定应返回验证错误。

每个地址族只绑定一个源地址；“绑定一部分”指部分流量或只绑定其中一个地址族，不代表从多个 IPv6 随机轮换。地址池轮换是独立后续需求。

系统默认 `direct` 为保留出口。自定义 tag 从不可变 ID 派生，名称修改不改变 tag；避免与内建 tag 冲突。策略通过 ID 引用出口，渲染时才转换为 tag。

### 4.2 地址失效

固定绑定采用严格语义：指定地址不可用时相关连接失败，不悄悄切回系统默认地址。探测失败、地址缺失和数据过期分别展示，不自动归为同一类故障。

保存策略可以使用最近已知地址；发布前缺失地址明确阻止发布，过期数据要求先刷新验证。agent 应用前再次检查所需绑定地址；失败则保留 last-good 配置并上报原因。为此发布元数据需携带该版本的绑定约束与所需能力，避免 agent 自行猜测任意 JSON。

地址在运行中消失时先报告故障，不自动停止整个 sing-box，不影响同节点其他出口。绑定验证只能证明检查时可用，无法避免检查后立即变化。服务仍运行也不证明出口健康，管理页需显示运行时地址异常。

## 5. 第二阶段：用户策略与部分流量

### 5.1 可理解的第一版规则

在用户的节点绑定详情设置一个策略：

- 默认出口：未命中规则时使用的出口。
- 有序规则：目标域名/后缀、目标 CIDR、目标端口或范围、TCP/UDP，以及使用的出口或拒绝动作。
- 同字段多个值为 OR，不同字段为 AND；明确保留规则顺序，第一条命中的终结规则生效。
- 域名规则依赖客户端传递域名。第二阶段不默认启用 sniff，也不承诺对 IP 请求识别出所属网站。

例如：Alice 默认固定双栈出口，`example.com` 使用仅 IPv6 出口，指定网段走系统默认；Bob 全部使用另一个 IPv4 出口。

第二阶段基础范围不提供按“服务名称”匹配的抽象；现有 servicecatalog 是只读分类，不直接当成路由规则集。远程规则集、上游代理和出口组在后续引入。

### 5.2 与已有表的衔接

`route_profiles.rules_json` 使用明确的 schema version 保存业务规则 AST；将默认目标存为出口 ID，不能只依赖可改名的 `final_outbound_tag`。现有格式先清点、备份和显式迁移；不根据 JSON 外观自动猜版本。

第二阶段仅开放节点级策略，避免全局模板引用节点私有地址。每个用户节点绑定最多一个策略；无策略沿用现状。允许多个用户引用同一策略，编辑时预览全部受影响用户。

渲染器根据实际获准且将被渲染的 ProxyCredentials 展开该用户的 auth names。只路由已有授权连接，不因为选择了出口就创建 PathAccess 或新凭据。

引用中的出口和策略删除必须返回影响预览并阻止直接删除；提供显式替换关联后再删除。节点删除保留必要历史，禁用关联策略，沿用现有节点和授权撤销事务，不自动改为另一个同名节点。

## 6. 第二阶段：sing-box 编译策略与 IPv6-only

当前仓库构建 pin 为 `v1.14.2`。实现应针对发布 pin 检验配置与行为，不能只依赖会滚动更新的在线文档或旧的 `refs/sing-box` checkout。

### 6.1 常规出口

固定双栈出口示例（文档地址仅为占位，不可直接部署）：

```json
{
  "type": "direct",
  "tag": "egress-ID",
  "inet4_bind_address": "192.0.2.10",
  "inet6_bind_address": "2001:db8::10"
}
```

仅 IPv6 出口的解析配置：

```json
{
  "type": "direct",
  "tag": "egress-v6-ID",
  "inet6_bind_address": "2001:db8::10",
  "domain_resolver": {
    "server": "node-dns",
    "strategy": "ipv6_only"
  }
}
```

`node-dns` 必须有对应 DNS server 定义。DNS 传输自身的地址族和业务目标的地址族分别配置：仅 IPv6 的业务策略不意味着解析器也必须经 IPv6 访问。未配置新策略的节点不额外渲染 DNS 块，保持原默认输出。

### 6.2 严格语义由编译器保证

`domain_resolver.strategy` 只控制域名解析，直接传入 IPv4 不经过解析。因此 `ipv6_only` 不能仅渲染上述 outbound。

每条业务规则编译成相邻、不可被其他终结规则插入的片段：

1. 匹配该用户和目标条件，若目标是被禁止的 IP 地址族则拒绝。
2. 匹配相同条件，将剩余请求路由到指定出口；域名解析由该出口的 resolver 策略约束。

默认出口也必须编译出对应拒绝片段。作用范围必须和原规则完全一致：只对某个域名启用仅 IPv6 时，不可变成禁止该用户所有 IPv4 请求。

第二阶段避免在这些片段前增加全局 `resolve` 或地址改写。目标 CIDR 需要域名解析后匹配时，实现专门的解析阶段，并保证后续选择仅 IPv6 出口时不复用先前 IPv4 解析结果；这是测试门槛，不把简单的 `domain_resolver` 配置当作充分证明。严格模式若无法证明不会通过 IPv4 发起连接，阻止该规则组合发布，不自动降级。

仅 IPv6 的目标无 AAAA、直接提交 IPv4、IPv6 路由失败、固定地址失效时，均不回退 IPv4。IPv4-only 对称处理。优先模式允许另一地址族回退，但固定源地址不会因失败自动替换成其他源地址。

客户端通过 IPv4 连接服务器仍然可以使用 IPv6 出口。客户端提前把域名解析成 IPv4 后提交时严格模式会拒绝；订阅说明需提醒使用域名请求或 IPv6，不能承诺透明转换 IPv4 目标。

### 6.3 确定性与兼容

用户规则顺序固定；无序地址、凭据、出口引用按稳定 ID 排序并去重。同样的业务配置必须生成相同字节和 hash；探测时间、延迟、最近观测公网地址等不进入配置 hash。

旧节点无新策略时保持默认配置和行为。新策略发布校验 agent 能力及 sing-box 兼容性；不能从 agent 支持地址发现推断 sing-box 支持所有出口字段。配置应用继续使用完整渲染、版本发布、`sing-box check`、原子替换、观察服务和 last-good 回退。

## 7. API 与界面

以下为拟议接口，最终命名与现有路由风格对齐，均使用不可变资源 ID：

| 接口 | 用途 |
| --- | --- |
| `GET /api/admin/nodes/{id}/addresses` | 本机地址、探测结果、采集新鲜度 |
| `GET/POST /api/admin/nodes/{id}/outbounds` | 列表和创建节点出口 |
| `PATCH/DELETE /api/admin/outbounds/{id}` | 更新或删除出口，验证依赖 |
| `GET/POST /api/admin/nodes/{id}/route-profiles` | 节点策略列表和创建 |
| `PATCH/DELETE /api/admin/route-profiles/{id}` | 编辑策略，展示影响 |
| `PATCH /api/admin/bindings/{id}/routing` | 设置或清除用户节点策略 |

第一阶段仅交付地址读取 API，以及第 3.2 节的 agent 快照报告 API；表中的 outbounds / route-profiles / routing 接口属于第二阶段。无地址历史接口。错误状态遵守现有 admin API 约定；不存在的资源显式返回 404。第一阶段增加 `network.inventory.v1`，能力缺失显示为“不支持”，不是“没有地址”。第二阶段再增加发布约束验证能力，复用配置预览和发布入口，不因保存表单立即重启 sing-box。

界面设计：

- 第一阶段节点详情增加“地址”：分别显示本机 IPv4/IPv6、接口/状态、Server 观测 IPv4/IPv6、采集时间和是否过期。当前入口单独显示，不能误标为自动发现。只展示当前状态，无历史表格或“用作入口”的新操作。
- 第二阶段节点详情增加“出口”：表格显示地址族、绑定地址、引用人数、草稿/已发布配置与运行异常。
- 第二阶段用户节点绑定增加“出口策略”：先选默认出口，通过“添加规则”展开部分流量设置。
- 第一阶段直接更新地址状态，不建设独立变化通知中心。第二阶段绑定地址缺失时在引用出口处显示异常；不接入外部通知服务。
- 使用原生 Kumo、TanStack Query/Table、react-hook-form/zod；浏览器只呈现服务端返回的状态，不自行推断地址失效。

## 8. 自动切换与高级能力的边界

### 8.1 入口地址自动跟随：待决策

如果以后启用，给 NodeHost 增加明确的来源策略，例如“跟随指定接口稳定公网 IPv4”，而不是从地址列表随便挑一个。保留 Host ID 和关联 Endpoint / Path，优先保护手动域名，采用去抖、候选确认和回退记录。

Server 获知变化只能改善发布端速度；客户端恢复还取决于订阅刷新、DNS 缓存和重连，已有 TCP 会话不能迁移。没有独立的客户端更新机制，就不承诺秒级恢复。

### 8.2 出口组：后续独立阶段

在固定出口稳定后评估 `selector` 和 `urltest`。手动切换需要管理控制通道；当前仅编译了 Clash API，并未配置，不能为此默认开放。需定义鉴权、loopback 监听、agent 中介、期望选择与运行时选择同步、重启恢复和回滚，再实现运行时切换。

`urltest` 的结果只代表到探测 URL 的表现；切换通常影响新连接，打断旧连接应显式设置，不称作连接迁移。对固定身份出口，自动更换公网 IP 可能违背用户意图，默认关闭自动选择。

### 8.3 暂不纳入

地址池随机轮换、自动配置额外 IPv6、NAT64、按 Path 分离凭据、服务端代理链、netns、策略路由标记、远程规则集和 TLS 分片均不作为本计划首期依赖。后续有具体场景再分别设计，避免一次暴露所有 sing-box 参数。

### 第一阶段 A：采集和来源解析验证

- [ ] 引入 netlink v1.3.1 候选，验证目标节点的地址字段、订阅、关闭、权限失败和轮询恢复。

### 第一阶段 B：agent、Server 与当前状态存储

- [x] agent 启动采集，订阅事件后去抖刷新，周期校准；独立发送最新完整快照，故障重试不阻塞心跳、配置和计费。

- [x] 成功快照事务替换当前地址 JSON 集合，失败快照保留最近成功数据并标记错误；不保存历史快照或 IP 变更明细。

验收：加减地址可被观察；失败采集不误删，ACK 丢失和乱序不覆盖更新状态；断线显示过期；暂停节点仍采集，删除节点 token 不能继续写入。

### 第二阶段 A：出口策略兼容性验证

- [ ] 盘点既有出口/策略/Proxy JSON，明确旧格式迁移规则。
- [ ] 用发布 pin 验证 VLESS-Reality/SS2022 的按用户 TCP/UDP 分流、双栈绑定、严格 v4/v6、IP 请求、预解析和 CIDR 组合。

## 10. 验证与交付约束

- 单元测试通过注入网卡采集器、事件源和 HTTP transport 验证去抖、超时、重试、乱序；不依赖真实网卡变化、sing-box 或 systemctl。
- DB 测试使用临时 SQLite，覆盖幂等、旧格式迁移、引用删除和同名节点重建隔离。
- renderer golden 覆盖所有地址族和选择范围；对 source / resolver / tag / auth names 做交叉断言。
- 部署 smoke 使用 pin 对真实双栈测试环境验证 TCP/UDP、VLESS/SS2022、目标观测地址、DNS 无 AAAA 和撤销源地址；`sing-box check` 通过只证明配置有效，不能代替行为验证。
- 记录 agent 在大量 IPv6 地址、断网和探测超时下的 RSS、CPU、请求数和快照大小；第一阶段 A 固定测试规模及资源阈值，后续使用同一基线验收。
- UI 完成后运行 Playwright 并检查渲染几何和计算样式，覆盖窄屏、错误态、缺能力和过期状态。
- 实现阶段执行 UI build、`go test ./...`、`go vet ./...`；新增迁移并同步 `schema/schema.sql`，不改 main 已有迁移。
- 仅写本文档时不执行上述运行时测试，不将计划勾选为实现完成。

## 11. 默认建议与待决策项

已确认：第一阶段同时交付 agent 本机地址发现和 Server 公网观测，只保存当前状态，不建设 IP 历史；第二阶段实施出口策略。两阶段均不自动切换入口，先 HTTP 上报，不依赖其他计划中的 WSS。第二阶段固定地址失效不回退，用户策略按用户节点生效。

实现前需要确定的产品选项：

1. 是否接受“仅 IPv6 导致只支持 IPv4 的目标无法访问”的严格语义（本文推荐接受，不做隐藏转换）。
2. 第二阶段同时支持源 IPv4、源 IPv6，字段和校验对称。
3. 入口自动跟随是否值得做，以及依赖订阅还是域名更新（本文保持待评估）。
