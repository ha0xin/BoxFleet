# 连接审计可靠传输与 ClickHouse 实施计划

更新于 2026-10-07。状态：计划已整理，尚未实施持久发送队列、WSS 或 ClickHouse。阶段按依赖顺序推进，不将候选库或试验结果视为生产验收。

## 目标与边界

让连接审计在网络中断、agent/server 重启时可重放；提供低延迟上报；在单机中央服务器上验证更大规模的审计存储和查询。发生不可恢复损失时，应能看到缺口，而不是继续显示“完整”。

- 节点保留薄 agent + sing-box，不部署数据库、Docker 或完整 Collector。
- SQLite 继续管理业务、凭据、配置和计费；ClickHouse 只承接审计数据。
- v2ray 计数继续承担计费；连接流字节是观测估计，不能升级为账单依据。
- 配置拉取、升级、暂停/删除和 token 撤销维持现有语义。
- 优先复用成熟库，不自行设计 WebSocket 协议实现或 WAL 文件格式。
- 本计划不启动 GeoIP、国家分布等此前延期的分析功能。

设计依据：[现状及故障边界](realtime-telemetry-and-recovery.md)、[prior art 与参考代码](telemetry-prior-art.md)、[ClickHouse 研究](clickhouse-network-audit-plan.md)。参考提交及文件校验和见 [manifest](references/telemetry-prior-art-manifest.json)。

## 组件选择

| 组件 | 计划 | 决策门槛 |
| --- | --- | --- |
| 节点队列存储 | 比较 `tidwall/wal` 与 `nsqio/go-diskqueue`，只选一套 | 写入持久边界、ACK 前保留、损坏/磁盘满恢复、节点峰值内存通过验证 |
| WSS | 首选评估 `coder/websocket` | 与 HTTP 共用认证、幂等和 ACK；读限制、Ping、退出及重连通过测试 |
| 重试 | 复用现有 `sethvargo/go-retry` | 指数退避、随机抖动、取消及错误分类明确 |
| ACK 检查点 | 复用现有 renameio | 与队列回收的提交顺序正确，验证目录项持久性 |
| ClickHouse 客户端 | 评估官方 `clickhouse-go/v2` | 固定服务端/驱动版本，批量与失败重放结果正确 |
| 中央通用采集管道 | 可评估 Vector，或使用薄 Go 写入器 | 避免同时维护两套队列；确认端到端 ACK 与累计快照语义 |

参考 Vector 的确认后回收、OTel 的在途项恢复、Filebeat 的 ACK 游标/校验、Fluent Bit 的 chunk 确认。它们与各自框架耦合的代码不直接搬入 agent。Kafka/NATS 不作为第一阶段依赖。

## P0：确认数据口径和资源基线

- [ ] 采样至少一天的真实报告：报告数、会话数、快照更新数、平均/峰值大小、写入速率和查询延迟。
- [ ] 核验节点版本、启用配置、最新报告和真实连接事件；无流量节点用可控连接验证，不能凭心跳判定采集正常。
- [ ] 定义 ACK 含义：默认代表服务端已持久接受；如仅进入中央持久队列，明确区分已接受与已可查询。
- [ ] 定义队列字节上限、目标可承受断线时间、fsync 周期与崩溃损失窗口；据实测定值，不按代理流量 GB 推算。
- [ ] 明确连接/旧聚合/coverage/journal 的幂等与缺口口径。

验收：形成可复现的数据样本与指标记录；确认 24GB 主机上的实际余量。此前 8–12GB ClickHouse 数字仅是预算，不是最低要求，不预留固定 3GB 给轻负载 bfs。

## P1：选定队列库并完成故障 PoC

- [ ] 固定候选版本，审查许可证、依赖及维护状态。
- [ ] 读取不消费；业务 ACK 后才能回收。每条记录身份和内容不可变。
- [ ] 验证 Put/Write 的返回是否包含所需同步，错误是否返回调用者；不能以“异步写入已入队”承诺持久化。
- [ ] 测试损坏尾记录、截断、磁盘满、同步失败、异常退出、重开、重复 ACK、容量回收及单进程所有权。
- [ ] 测量节点低流量/峰值内存及磁盘开销；批量 fsync 与低延迟取舍写入决策记录。

验收：选一套存储库；每个关键崩溃点的结果为可重放、已确认，或显式缺口，不允许静默消费未确认数据。现有 Peek/Read 试验只作起点。

## P2：先通过 HTTP 实现可靠多批次上报

- [ ] 采集器外增加有上限的交接缓冲和队列写入工作线程；sing-box Recv 不等待磁盘或远端网络。
- [ ] 复用报告结构，持久保存批次及 `(agent_boot_id, sequence)`；agent 重启保留未确认批次原身份。
- [ ] 用多批次队列替代单 PendingConnections 槽的限制，并定义旧状态迁移：先恢复旧未确认报告，再发送新数据。
- [ ] 服务端认证得到 node_id；报告处理与去重在事务中完成，提交后才成功响应。
- [ ] ACK 丢失重发原批次；累计快照按 MAX、旧桶按增量、coverage 按报告幂等处理。
- [ ] 明确永久错误、可重试错误、撤销/暂停/删除行为；永久失败不得静默丢数据，隔离或停止发送并暴露诊断。
- [ ] 系统日志游标只在达到约定持久边界后推进；协调 journal 保留及队列容量，不宣称可恢复已轮转日志。
- [ ] 拆开控制轮询与审计发送调度，避免配置请求阻塞或审计积压拖延心跳、计费。

验收：服务端停机后恢复、agent 重启及响应丢失不造成双计数；达到队列上限时不拖垮代理业务，并保留丢失区间/原因。HTTP 仍为默认兼容通道。

## P3：增加 WSS 低延迟通道

- [ ] 节点主动发起 WSS，复用 bearer token，协商协议版本；HTTP 与 WSS 调用同一业务处理逻辑。
- [ ] 定义 report/ack 消息、最大长度、在途窗口及握手失败的 HTTP 回退。
- [ ] 使用库实现 Ping、读循环、超时和关闭；重连复用已有退避库。
- [ ] 不以网络 Write 成功代替业务 ACK，重连从未确认队列恢复。
- [ ] 实测 Cloudflare Tunnel 路径下的空闲连接、网络切换、代理重启和服务端退出。
- [ ] 以短周期批量发送实现低延迟，不逐事件写数据库。浏览器实时刷新可另用 SSE，无需绑定节点协议。

验收：HTTP/WSS 切换无重复计数；token 撤销和节点删除仍能切断访问；低延迟指标与常规批量成本实测满足 P0 定义的目标。旧 agent 继续工作。

## P4：单机 ClickHouse PoC 与影子写入

P0 后可开展离线 PoC；线上影子写入依赖 P2 的可靠接受与重放边界。

- [ ] 中央部署单机 ClickHouse，内部访问；SQLite 业务/计费保持原位置。
- [ ] 保存连接快照、报告/coverage 与旧聚合来源，验证连接身份和规范状态查询。
- [ ] 严禁对累计快照直接 SUM；验证乱序更新、跨日连接、来源切换及历史回填。
- [ ] 保留明细后再优化分区、排序键、投影和汇总；不能以后台最终去重代替实时正确性。
- [ ] 用真实样本及 10 万/100 万/1,000 万行验证 Top N、用户/节点筛选、详情与时间图。
- [ ] 限定查询/后台任务/容器资源，测量与 bero 开发编译并行时的负载；不提前增加 broker 或集群。
- [ ] 少量节点影子写入，对照 SQLite；服务端或 ClickHouse 停机时，重放和管理/计费可用性分别验证。

验收：明确 24 小时/7 天/90 天查询的 P50/P95、parts/合并积压、内存及磁盘需求；正确性对照通过，写入积压可恢复，备份可还原。保留周期及性能目标以实测结果确认。

## P5：灰度读取、回填与运维交付

- [ ] 在既有 facade 边界切换审计存储；分页、系列、过滤及服务分类共用规则。
- [ ] 按水位回填，区分旧 journal、聚合桶和连接状态，不虚构历史域名字节。
- [ ] 展示“活动中 / 已关闭”及最后观测时间；过期或断线单独提示，不自动伪造关闭。
- [ ] 提供队列字节/年龄、最后 ACK/报告、采集 reset/drop/gap 与存储延迟的诊断。
- [ ] 灰度期间保留可用的旧读取路径或持续镜像；切换后验证数据库回退与备份恢复。不能关闭旧写入后仍宣称旧库随时可无损回退。
- [ ] 单列历史清理方案；只有切换条件满足后才清理旧审计来源，保留计费和业务数据。
- [ ] 更新部署、升级、恢复及库版本维护文档。

验收：生产灰度运行、故障恢复与回退演练完成；旧来源退出按 roadmap 既有条件执行。节点突发断电和上游未采到的事件仍按已验证的损失窗口及缺口说明，不承诺绝对零损失。

## 验证边界

协议、队列和数据库用进程级集成测试及故障注入验证；普通单元测试不启动真实节点服务。实节点/Cloudflare 验证属于灰度 smoke 流程。本次遵照用户要求不运行浏览器端到端检查。

本计划的完成标志是各阶段验收通过，不是“引入了成熟库”或“WebSocket 已连上”。
